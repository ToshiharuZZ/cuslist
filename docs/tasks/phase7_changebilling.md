# Task: プラン変更・解約機能 (Plan Change & Cancellation)

## 概要
利用者が自身の契約プランを変更・解約できる機能を実装する。プラン変更時の料金計算、解約予定日の管理、履歴記録を含む包括的な機能を提供する。

## 目的
- ユーザーエクスペリエンスの向上（自己管理機能の提供）
- プラン変更時の適切な料金計算の実現
- 解約プロセスの透明性確保
- 管理者による柔軟な契約管理機能の提供

---

## 1. 機能要件

### 1.1 プラン変更機能

#### 1.1.1 ユーザー自身によるプラン変更
- **即時変更**: ユーザーがプランを選択し、即座にプラン変更を実行
- **変更可能なパターン**:
  - アップグレード: Basic → Standard → Premium
  - ダウングレード: Premium → Standard → Basic
  - 課金方式変更: サブスクリプション ⇄ 従量課金 ⇄ トランザクション ⇄ ハイブリッド

#### 1.1.2 プラン変更制限ルール
- **変更頻度制限**: 1ヶ月に1回まで（不正な繰り返し変更の防止）
- **ダウングレード時の制約**:
  - 現在の顧客登録数が新プランの上限を超える場合は変更不可
  - 事前に顧客データの削減を促すメッセージを表示
- **即時適用**: プラン変更は即座に反映され、次回アクセスから新プランの制限が適用される

#### 1.1.3 プラン変更時の料金計算
- **日割り計算方式**:
  - 現プランの残り日数分を日割りで計算し、次回請求時に調整
  - アップグレード: 差額を即座に請求（または次回請求に上乗せ）
  - ダウングレード: 返金はせず、次回請求から新料金を適用
  
- **計算式**:
  ```
  残日数 = 月末日 - 変更日
  日割り額 = (新プラン月額 - 旧プラン月額) × (残日数 / 当月日数)
  ```

- **従量課金/トランザクション型への変更**:
  - サブスクリプション型から変更する場合、残り期間分の返金は行わない（利用規約に明記）
  - 従量課金型からサブスクリプション型への変更は即日適用

### 1.2 解約機能

#### 1.2.1 解約申請
- **即時解約**: 解約申請後、即座にアカウントが無効化される
- **月末解約**: 当月末まで利用可能、翌月1日から無効化
- **解約予約**: 指定した日付に自動的に解約（最大3ヶ月先まで）

#### 1.2.2 解約時の処理
- **データ保持期間**: 解約後30日間はデータを保持（再契約時に復元可能）
- **完全削除**: 解約後30日経過したアカウントのデータを自動削除
- **解約理由の記録**: 解約理由を選択肢 + 自由記述で収集（サービス改善のため）

#### 1.2.3 解約制限
- **課金残高がある場合**: 未払い料金がある場合は解約不可（要決済）
- **管理者アカウント**: 他に管理者が存在しない場合は解約不可（最低1名の管理者必須）

#### 1.2.4 再契約
- **30日以内の再契約**: 以前のデータを復元して契約再開
- **30日経過後の再契約**: 新規アカウントとして扱い、データは引き継がれない

### 1.3 管理者向け機能

#### 1.3.1 利用者のプラン変更
- 管理者が任意の利用者のプランを変更可能
- 変更理由の記録（例: 特別対応、サポート案件、営業施策など）
- 変更履歴の管理者ログへの記録

#### 1.3.2 利用者の強制解約
- 管理者が利用者を強制的に解約可能（規約違反時など）
- 強制解約理由の必須記録
- 強制解約されたアカウントは再契約不可フラグを設定可能

## 6. セキュリティ考慮事項

### 6.1 認証・認可
- **CSRF保護**: 全てのPOSTリクエストにCSRFトークン必須
- **セッション検証**: プラン変更・解約実行時にセッションの整合性を再確認
- **権限チェック**: 自分自身のプランのみ変更可能、管理者は全ユーザー変更可能

### 6.2 データ整合性
- **トランザクション制御**: プラン変更時は users.csv と plan_change_history.csv への書き込みをアトミックに実行
- **ロールバック機構**: エラー時は変更前の状態に戻す
- **二重実行防止**: 変更処理の冪等性を確保（同じリクエストの重複実行を防ぐ）

### 6.3 データ保護
- **解約データの暗号化保持**: 解約後もデータは暗号化されたまま保持
- **完全削除の確実性**: 保持期限後のデータ削除は物理削除を保証
- **ログ記録**: プラン変更・解約の全操作をログに記録（監査証跡）

## 10. 想定される課題と対策

### 課題1: プラン変更時のデータ整合性
**問題**: プラン変更中にエラーが発生した場合、データが不整合になる可能性
**対策**: トランザクション制御の実装、ロールバック機構の整備

### 課題2: 大量の解約データ蓄積
**問題**: 解約履歴が増え続けるとパフォーマンスが低下
**対策**: 1年以上前の解約履歴をアーカイブ化（別ファイルに移動）

### 課題3: バッチ処理の失敗
**問題**: データ削除バッチが失敗した場合、期限切れデータが残り続ける
**対策**: エラー通知機能の実装、リトライ機構の追加

### 課題4: 日割り計算の複雑性
**問題**: 月の途中での変更、うるう年対応など、計算が複雑
**対策**: 徹底的な単体テスト、境界値テストの実施

## メモ

- この機能は既存のbilling_serviceと密接に連携する
- プラン変更時は即座にセッション情報を更新し、次のリクエストから新制限を適用

- CSVベースのシステムのため、トランザクション制御に注意が必要
- 将来的にデータベース移行を検討する場合も、このロジックは流用可能な設計とする
