# システム開発作業計画書

本ドキュメントは、`docs`配下の要件定義書および詳細設計書に基づき、システム開発の作業計画をまとめたものである。

## 1. 文書分析と洞察 (Deep Insight)

既存のドキュメント（`specs1.md`, `specs2.md`, `cuslist_detail.md` 等）を分析し、以下の技術的課題と重要ポイントを抽出した。

### 1.1. 技術的制約と課題
*   **暗号化データの検索パフォーマンス**
    *   要件: 顧客情報はAESで暗号化して保存されるが、検索機能が必須である。
    *   課題: 暗号化された状態では部分一致検索や範囲検索が不可能である。
    *   対策: 検索時はCSVデータをメモリ上に読み込み、復号した上でフィルタリングを行う実装が必要となる。これにより、データ件数が増加した際のメモリ圧迫と処理遅延が懸念される（`specs1.md`の非機能要件でも言及あり）。初期段階ではメモリ処理で進めるが、将来的な分割保存やインデックス化の設計を考慮する必要がある。
*   **CSVファイルの同時アクセス制御（排他制御）**
    *   要件: Webベースでの複数人利用が想定される。
    *   課題: データベースを使用しないため、同時に書き込みが発生した場合のデータ破損リスクがある。
    *   対策: ファイルロック機構（`fcntl` や `lockfile` 等）を実装し、厳密な排他制御を行うデータアクセス層（DAO）の構築が不可欠である。
*   **課金ロジックの複雑性**
    *   要件: サブスクリプション、従量、トランザクション、ハイブリッドと多岐にわたる課金モデル。
    *   課題: コードが複雑化しやすく、保守性が低下する恐れがある。
    *   対策: Strategyパターン等のデザインパターンを適用し、課金ロジックをプランごとに分離・カプセル化する設計を行う。

### 1.2. データ整合性の確保
*   `users.csv`（利用者）と `billing.csv`（請求）の整合性維持が重要。
*   操作ログ（`logs.csv`）が従量課金の根拠となるため、ログ保存の失敗は許容されない（トランザクション的な処理が必要）。

## 2. システムアーキテクチャ策定

### 2.1. 技術スタック選定
*   **言語**: Python 3.x
*   **Webフレームワーク**: **Flask**
    *   選定理由: DjangoはRDBMSとの結合が強いため、CSVベースの軽量管理という要件にはFlaskが適している。
*   **暗号化**: `cryptography` ライブラリ
*   **フロントエンド**: HTML5, CSS3 (Vanilla), JavaScript (Minimal)
*   **データ保存**: CSVファイル

### 2.2. ディレクトリ構成案
```text
project_root/
  ├── app/
  │   ├── models/       # CSV操作・暗号化ロジック (DAO)
  │   ├── views/        # 画面処理・ルーティング
  │   ├── services/     # 課金計算・バリデーション等のビジネスロジック
  │   ├── static/       # CSS, JS
  │   └── templates/    # HTMLテンプレート
  ├── data/             # CSVファイル格納 (git無視)
  ├── docs/             # ドキュメント
  └── tests/            # テストコード
```

## 3. 開発ロードマップ

開発を以下のフェーズに分割し、段階的に進める。

### Phase 1: 基盤実装 (Foundation)
**目的**: データの読み書きとセキュリティ基盤の確立
1.  **プロジェクトセットアップ**: Flask環境構築、Git初期化。
2.  **共通モジュール開発**:
    *   `CsvHandler`: ファイルロック付きのCSV読み書きクラス。
    *   `CryptoManager`: AES暗号化・復号、ハッシュ化を行うクラス。
    *   `Logger`: 操作ログを記録するクラス。
3.  **単体テスト**: 基盤モジュールのテスト実装。

### Phase 2: 利用者管理機能 (User Management)
**目的**: セキュアな認証機能の実装
1.  **利用者モデル実装**: `User` クラス、`users.csv` 操作の実装。
2.  **認証機能実装**: ログイン、ログアウト、セッション管理。
3.  **利用者管理画面**: 管理者による利用者登録・削除機能。

### Phase 3: 顧客管理機能 (Customer Management)
**目的**: コア機能である顧客リスト管理の実装
1.  **顧客モデル実装**: `Customer` クラス、`customers.csv` 操作の実装。
2.  **CRUD機能実装**:
    *   一覧表示（復号処理含む）。
    *   新規登録（暗号化保存）。
    *   編集・削除。
3.  **検索機能実装**: メモリ上での復号・フィルタリング処理。

### Phase 4: 課金・制限機能 (Billing & Limits)
**目的**: 収益化機能の統合
1.  **課金ロジック実装**:
    *   プラン判定ロジック。
    *   制限チェック（登録数、検索回数）。
2.  **ミドルウェア実装**: 各操作前にプラン制限を確認するデコレータ等の実装。
3.  **請求管理機能**: 操作ログに基づく料金計算と `billing.csv` への記録。

### Phase 5: UI/UX改善・統合 (Refinement)
**目的**: 使いやすさと見た目の向上
1.  **画面デザイン適用**: CSSによるスタイリング（要件にある「モダンでプレミアムなデザイン」を意識）。
2.  **エラーハンドリング**: ユーザーフレンドリーなエラーメッセージ表示。

### Phase 6: テスト・品質保証 (QA)
**目的**: バグ修正とリリース準備
1.  **結合テスト**: シナリオベースのテスト（ログイン〜顧客登録〜課金確認）。
2.  **負荷テスト**: 大量データ時の検索パフォーマンス確認。
3.  **セキュリティチェック**: 暗号化漏れがないか、アクセス制御が正しく機能しているか確認。
