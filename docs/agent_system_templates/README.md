# 🚀 Gemini Agentic Workflow System (GAWS) テンプレート

このディレクトリには、プロジェクト「cuslist」で確立された、高効率・高品質なAIエージェント開発ワークフローのテンプレート一式が含まれています。

新規プロジェクトを開始する際、これらのファイルをコピーしてカスタマイズすることで、初日から高度に組織化された開発体制を構築できます。

## 💎 コア・コンセプト

このシステムは以下の3つの柱で構成されています。

### 1. 探索型・影響分析 (Exploratory Impact Analysis)
既存のPhase番号に縛られず、実ファイルやタスクを**動的に探索**して影響を特定します。
- 手戻りの防止
- ドキュメントと実装の乖離防止
- **ドメイン・エージェント制の維持**（エージェント数の肥大化防止）

### 2. 厳格な品質保証 (Strict QA Gate)
**Reviewer Agent** の承認、および **GAWSガードレール** による機械的検証が必須。

### 3. 自律的な状況報告 (Autonomous Reporting)
各ドメインの専門家が自律的に進捗を更新。

## 🏛 戦略的組織構成とエージェント・アーキテクチャ分析

GAWSのテンプレートは、単なるツールの集まりではなく、大規模・高難易度プロジェクトを「AIエージェントの自律性」と「統治の見通し」の両立によって完遂させるための**戦略的組織構造**を採用しています。

### 1. 三層構造の戦略レイヤー

プロジェクトを以下の3つの権力・情報レイヤーに分離することで、意思決定の速度と安全性を最大化します。

| レイヤー | 構成エージェント | 戦略的焦点 | 役割 |
| :--- | :--- | :--- | :--- |
| **戦略 & 指揮 (Strategy & Command)** | Manager, Impact Analysis | **「何を行うか(What)」** | 全体最適、リソース割当、アーキテクチャ上の整合性、統治規定の遵守。 |
| **統治 & 防護 (Governance & Shield)** | Reviewer, Security | **「正しく行われているか(Right)」** | 品質・安全のゲートキーパー。コード品質、セキュリティ監査、コンプライアンス。 |
| **検証 & 保証 (Verification & Validation)** | **Test Specialist** | **「期待通りか(Reliable)」** | 振る舞いの正確性、網羅性、パフォーマンス、統計的精度の立証。 |
| **実行 & 実現 (Execution & Build)** | Backend, Frontend, Domain Specialists | **「どう実現するか(How)」** | ドメイン別の深い専門知識、実装効率、技術的整合性。 |

### 2. 権限と均衡 (Checks and Balances)

AIエージェントによる「自作自演（利益相反）」を防ぐため、以下の均衡構造を組み込んでいます。

- **Manager vs Expert**: Managerはコードを書かない（兼務禁止）。実装者が「早く終わらせたい」という圧力で品質を妥協するのを防ぐ。
- **Expert vs Test Specialist**: 実装者は自らの正当性を主張するが、Test Specialistはそれを「破壊」しようと試みる。この対立関係が堅牢性を生む。
- **Expert vs Reviewer**: 実装者は自ら承認できない。必ず第三者（Reviewer）がソースコードを静的・動的に検証する。
- **Strategy vs Execution**: 新機能の開始（Strategy）は、常に影響分析（Impact Analysis）による「既存破壊のシミュレーション」を経てから実行レイヤーへ落ちる。

### 3. 情報伝達の「シングル・ソース・オブ・トゥルース (SSoT)」

エージェント間、および人間とエージェント間の認識齟齬を防ぐための動線設計。

- **`project_status.md`**: 全体の鳥瞰図。
- **`docs/reports/`**: 各実行レイヤーからの戦術報告書。
- **`docs/rules/`**: 憲法。Managerも逆らえない絶対的な統治基準。

### 4. スケーラビリティ戦術

プロジェクトの拡大に伴う「エージェントの肥大化」を抑えるためのガイドライン。

- **ドメイン帰属の原則**: 機能を「Phase（時間軸）」ではなく「Domain（機能軸）」で管理する。
- **メタ認知宣言**: 1つのLLMセッション内で複数の役割を演じ分ける際、宣言を行うことで役割ごとのバイアス（焦り、妥協、慢心）をリセットする。

## 📝 エージェント設計の黄金律

> **「安易にエージェントを増やすな。職能別ドメインに帰属させよ」**

タスクが発生するたびにエージェントを新規作成（Phase X Agent等）するのではなく、**Backend, UI, Analysis, Security** などの常設ドメインにアサインしてください。
これは、特定ファイルの「歴史的経緯（context）」を同一ドメインのエージェントに蓄積させ、一貫性を保つための戦略的判断です。
